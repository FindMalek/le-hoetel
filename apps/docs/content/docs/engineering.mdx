## Stack

- pnpm workspace and turborepo, TypeScript everywhere, biome for format and lint plus oxlint
- Next.js app router for `apps/web` (landing and public guest pages) and `apps/dashboard` (login and the hotel and admin app)
- `apps/api`: oRPC on bun. The only app that touches the database, auth, storage and providers
- Postgres with drizzle, better-auth, zod-validated env, shadcn components

## The rule: the api only touches the database

`apps/api` is the only app that touches the database, auth, storage and providers. `web` and `dashboard` call it through `@ritorno/orpc`, so secrets and data access live in one place. Never import `@ritorno/db` from `web` or `dashboard`.

## Conventions

- **oRPC:** procedures live in `packages/orpc/src/routers`, built from `publicProcedure` or `protectedProcedure`. Validate input and output with zod. Throw `ORPCError`, never raw errors.
- **drizzle:** the schema is in `packages/db/src/schema`. Change the schema, then run `pnpm db:generate`. Never hand-write a migration.
- **better-auth:** configured once in `packages/auth`. Sessions are cookies, signed-in calls send `x-csrf-token: orpc`.
- **env:** every variable goes through `packages/env` and `.env.example`. App code reads env through `packages/env`, not `process.env`. No secrets in diffs.
- **UI:** reuse shadcn components from `@ritorno/ui` and the theme tokens. No hard-coded colors.
- **RTL:** English, French and Arabic everywhere. Use logical CSS properties (`ms-`, `me-`, `ps-`, `pe-`, `start`, `end`), never left or right.
- **Files:** kebab-case. React components have a kebab-case file and a PascalCase export. Functions and variables are camelCase, module constants are UPPER_SNAKE_CASE.
- **Code:** explicit types, no `any`, short functions, no duplicate types or helpers, no comments that restate the code, smallest diff that does the job.

## Product rules the code must keep

- Every guest row and every query is scoped by hotel id.
- Guests are not auth users.
- Consent is logged per channel in an append-only log.
- Never log a phone, email or name in plain text.
- Previews, tests, local and staging never send real messages.

See [data and consent rules](/docs/data-rules) and [decisions](/docs/decisions).

## Tests

- One focused test per behavior or bug: it fails before the fix and passes after.
- No happy-path padding, snapshot dumps, or tests of types or the framework.
- Test through the public function or endpoint. Mock only external boundaries, never our own modules.
- Tests run against a real Postgres. `createTestDb()` from `@ritorno/db/testing` gives a fresh migrated database and `createTestApp()` from `@ritorno/orpc/testing` the real services plus `signUp()` for signed-in clients (server side, so it needs no invitation).

### Accessibility and speed budgets

- `apps/e2e/tests/a11y.spec.ts` runs axe on the landing page, the QR capture page and the sign-in page in English and Arabic. Any serious or critical violation fails the e2e job.
- The `lighthouse` workflow runs Lighthouse CI on the landing page (`/`, `/ar`) and the QR capture page (en, ar) with the mobile throttling defaults, when a pull request touches `apps/web`, `pnpm-lock.yaml` or a package those pages ship. Budgets live in `apps/e2e/lighthouserc.json`, 3 runs per URL:

  | Budget | Capture | Landing | Runs compared |
  | --- | --- | --- | --- |
  | Largest Contentful Paint | 2500 ms | 2500 ms | median |
  | Cumulative Layout Shift | 0.1 | 0.1 | median |
  | Total Blocking Time (lab stand-in for INP) | 600 ms | 600 ms | best |
  | Script transfer | 250 kB | 300 kB | median |
  | Accessibility score | 0.95 | 0.95 | best |

  All of these block. The performance score (0.8) only warns, because it swings with the speed of the runner. Total Blocking Time takes the best run for the same reason. INP needs real interactions, so CI does not measure it.
